The accepted implementation is one owned first-creation transaction with a current
authorized User/session lock and existing strict authorized readiness observation,
authoritative current bundle/exact prior attestation, saved draft version and
server-bound explicit review/creation/disposition confirmation. Readiness is an
application claim observation, not provider freshness; no new TTL is introduced.
There are no personal-field/owner/Portfolio/policy/catalog overrides in the intent.

The server-only core has no completion HTTP route or final UI. Production policy
resolution remains `null`; it prevents any NEW completion even with valid data.
Attestation recording stays separate. A transaction-aware exact-bundle lookup runs
under the already-authorized User lock without nesting public attestation APIs.

One additive 019 table stores immutable receipt identifiers, saved draft version/
digest, exact request and review digests, contract/catalog revisions, exact twelve
document descriptors with an attestation-key FK, original attestation UTC time,
readiness observation/authz version, deferred key names and completion UTC time.
Existing tables/rows are not backfilled or upserted. Creation uses existing unique
owner/Profile/slug constraints and Profile version 1/private contact defaults.

Authorized structurally exact retries recognize the original durable intent before
current new-completion rules and return original IDs/time, never profile bodies.
Changed intent conflicts. Receipt recovery is authorized by current User and needs
no previous session secret; later authorized sessions can recover even with currently
unavailable policies. Neither path rewrites Profile, draft, timestamps or evidence.
Draft saves share the User lock: save-first invalidates old completion review;
completion-first blocks new saves, while an exact prior draft retry remains read-only.
Existing owners without receipts cannot be converted/overwritten by this operation.
Unknown COMMIT outcome requires receipt recovery; never delete potentially committed
Portfolio/Profile/evidence as compensation. Routing/publication bypass prevention
below remains a separately approved later integration dependency.

## Field contract

The seven connected editor values are all **required at first completion** under the approved field matrix, not at draft save. This does not establish perpetual requiredness for edits or publication; see R10. Recommended common rule (R1): strings only; valid UTF-8; lengths count Unicode code points and UTF-8 bytes, both inclusive. Require a non-whitespace character for nonempty values and reject Unicode Cc controls (LF permitted only in biography). Preserve exact text: no trim, Unicode normalization, case folding, transliteration, name splitting, escaping into stored data or truncation. Spaces and combining marks count. Escape on output and isolate user text with `dir=auto`/`bdi`.

Missing required keys, previously cleared nulls and whitespace-only strings block completion; no default or identity-claim fallback. Draft save still preserves omitted fields and removes only explicit nulls; empty string remains invalid. Completion reads the saved version, not an unacknowledged browser edit or a second field payload. Unsupported or old candidates remain private and editable; never silently replace them with a first select option. Unknown keys/corrupt stored payload fail closed without partial writes. Existing profile rows are outside this first-creation operation.

## Completion authority and atomic result (R9)

Future operation: one CSRF-protected explicit POST, private/no-store, behind a separate default-off completion capability (not enabled by draft or registration switches). Strictly allow-list the envelope; reject authority selectors, arbitrary fields, uploads and client timestamps. Recommend `expectedVersion` integer 1–2,147,483,647; version-bound operation ID `<version>:<32 lowercase hex>`; strict boolean `confirm_private_creation=true`; and conditional strict boolean acknowledgement of R7 deferred disposition. Bind the confirmation to a server-issued review context for the current User, draft version, contract/catalog revisions and exact presented bundle. Request echoes may detect staleness but never choose authoritative documents or revisions. No personal fields are resubmitted in this envelope.

For a new mutation, all these conditions must hold together:

1. Active PHP session and independently current `requireAuthenticatedUser()` result: active User, matching authorization version, idle/absolute lifetime; server context must match. Never accept User/Portfolio IDs, email or readiness from the request. Lock current User first and revalidate under that lock using the same serialization convention as draft/attestation operations.
2. `readAuthorizedOwnerReadinessObservation()` yields strict `email_verified === true` bound to that User, session authentication and authorization version. False/null/missing/malformed/expired/mismatched observations deny. This is an **application observation of a validated claim** at `observed_at`; it is not provider verification time, fresh Google data, recent credentials/MFA or proof that another sign-in refreshes upstream claims. Do not invent a new freshness TTL or stronger assurance policy here; follow [14](14-OWNER-PORTFOLIO-CREATION-READINESS.md).
3. Resolve the trusted current `OnboardingAttestationBundle` and require exact stored evidence for all twelve descriptor values: age/Terms/Privacy identifier, version, SHA-256 of exact presented bytes, and document language. Verify review presentation binding and recheck the current resolver at submission. A changed bundle requires presentation/affirmation again, not latest-row reuse. Age is 18+ self-attestation, Terms is acceptance, Privacy is acknowledgement, not blanket consent. No DOB or client-provided descriptor authority.
4. Require no existing Portfolio or completion row for a new creation; an existing owner without a receipt follows the preserved owner policy, never implicit completion or overwrite. Read compatible current saved draft under the User lock; expected version and review must match exactly. Validate all seven required fields/catalog membership together and verify deferred disposition. A draft version of 0, last-section value, preview navigation or Portfolio existence proves none of this. All intended edits must first be acknowledged as saved.
5. Explicit current confirmation; no GET, implicit Continue, prechecked action or save constitutes final creation. Atomically claim the validated canonical slug with the existing unique index, not an availability precheck alone.

The operation owns one exception-mode PDO transaction and refuses an ambient caller transaction. In lock order User → draft/completion state → exact attestation evidence → new Portfolio/profile, create exactly one owned Portfolio with chosen slug, `is_published=0`, `published_at=NULL`; one `personal_info` row with mapped required facts, added columns, `profile_version=1` (R11), `public_contact_visible=0`, and other optional values null; then one immutable completion evidence row. All commit together. No project, contact exposure, publication, identity/account mutation or optional promotion occurs. The original draft payload/version/receipt/timestamps stay exact; completion-row presence freezes subsequent draft writes for this cohort. Only the committed profile/Portfolio supplies current data thereafter (R10).

Keep attestation recording separate and explicit via `recordOnboardingAttestations()` before completion; that API and `readOnboardingAttestations()` currently own transactions and cannot be nested in this transaction. Recommend a small shared internal exact-bundle lookup that can run under the already-authorized User lock, while public APIs retain their existing authorization/transaction contracts. Reuse descriptor validation and exact binary equality, not a new consent flag. A pre-recorded attestation remains historical evidence if completion fails; it does not imply completion.

Completion evidence recommendation: `user_id` PK; unique `portfolio_id`; FKs to User/Portfolio with explicit RESTRICT; completed draft version, contract revision, catalog revision, exact operation ID and canonical request SHA-256; all twelve exact descriptor columns referencing the existing composite attestation key; server UTC `completed_at DATETIME(6)`; and the accepted observation's application timestamp/authz version. Store a strict positive readiness result/confirmation and deferred-disposition evidence as enforced values or immutable contract semantics, with no session/token/subject or document/private answer bodies. Use bounded binary receipt/revision columns and the existing ID/version ranges; verify the exact schema in the normal additive migration runner. A retained draft can supply historical submitted answers; the mapped profile supplies initial and subsequently edited current values. Profile edits do not rewrite completion history. Receipt lookup must not require retaining/replaying the draft payload; any future approved draft deletion must leave current profile data and completion evidence intact, subject to separately reviewed rights handling.

Under the same User lock, check for a completion receipt before new-creation prerequisites: an authorized exact retry of the same operation/digest returns the original IDs/time/outcome without updates, even if draft/policy rules later change. This is receipt retrieval, not a new grant of completion/publication or bypass of current account/session authorization. Same ID with different input conflicts. Different operation ID after completion returns `already_completed` with a fixed private destination; it never overwrites. One receipt per User suffices for permanent first-completion retry; do not use the draft's evictable latest-save receipt as completion evidence. Bind digest to version, confirmations/disposition and server review/bundle/catalog/contract context; exclude CSRF/session secrets so a new authorized session can retrieve an uncertain result.

Same-User simultaneous requests serialize: identical retry gets the same result; different intent conflicts/already-completed. Different Users racing for one slug: the unique slug index chooses one winner; loser rolls back profile, Portfolio and receipt, retaining its draft and any separately recorded attestation. Reuse unique owner/profile indexes too. Classify only proven duplicate constraints as defined conflicts; other SQL/deadlock/storage errors roll back and return safe temporary failure. An uncertain COMMIT/network response requires exact-receipt lookup/retry, never compensating deletion or automatic new operation. Inject failure at each write and commit boundary in implementation tests. PHP session persistence is not distributed-transactional with MySQL: report uncertainty honestly and recover from the durable receipt after authorization.

**Draft** means candidate answers only; **completed** means committed private Portfolio/profile plus durable evidence from this operation; **published** means a later explicit authorized publication action. Neither a reserved slug, draft, attestation nor a preexisting Portfolio alone is completion. Disabling future capability gates prevents new operations; it never erases committed profiles, receipts or drafts. Prefer a reviewed forward repair over destructive rollback.

## Draft, current profile and publication lifecycle (R10)

**Observed behavior:** [profile form](../../owner_profile.php) loads `personal_info`, not onboarding drafts. Only `full_name` is required on `save_profile`; headline/title/contact/about/location/links are optional. Its completeness percentage is a presentation heuristic, not an onboarding or publication gate. The [save handler](../../includes/owner_actions.php) iterates the form's text allow-list, normalizes absent optional fields to empty strings via `submittedStringField()`, interprets an absent aggregate checkbox as false and copies the POST-time target's image key into a text save. The [persistence helper](../../includes/portfolio_scoped_data.php) can update supplied columns only, but has no expected-version predicate; it treats an unchanged existing row as success. Merely reading `$current` at POST time protects none of the values seen in an older browser form.

**Observed publication:** [publication route](../../owner_publication.php) requires the authorized owner, CSRF and existing limiter. `publishOwnedPortfolio()` requires a canonical, nonreserved saved slug and nonblank current `full_name`, then sets publication state; it does not validate all seven completion fields, attestations or the profile percentage. Public reads require a published Portfolio and active owning User. [Public profile projection](../../includes/public_lifecycle.php) includes name/title/headline/location/about/summary/social/image; email/primary phone only when aggregate `public_contact_visible=1`. [Private preview](../../owner_preview.php) reads current owner-scoped storage and can show saved private contacts. Editing a published profile currently changes its public projection on reload, without a staged publishing snapshot; do not promise publication review for every edit.

**Recommended authority:** draft → one-time validated completion → current profile/Portfolio → explicit publication. After completion, current `personal_info` and `portfolios` are authoritative for profile edits, preview and public output. Never rehydrate a profile form from a completed draft, dual-write edits back into it, refill cleared values from it, or merge its values during an old completion retry. An exact retry returns historical receipt IDs/time only (with navigation to the current profile); it must not return stale draft values as current data. A different old request conflicts/already-completed without writes. Freezing/retaining/deleting the historical draft is a separate decision; authority and edit safety must work regardless of retention duration. There is no deletion job or new retention schedule in this contract.

## Small profile-write concurrency contract (R11)

Recommend one additive `personal_info.profile_version INT UNSIGNED NOT NULL DEFAULT 1`, enforced range 1–2,147,483,647; initialize existing rows to 1 without changing their content/ownership/visibility. No version timestamp: existing `updated_at TIMESTAMP` has second precision and is not a safe compare token. No triggers, workflow/synchronization framework or version service. Draft `version`, completion receipt and profile version have distinct meanings.

1. A GET loads scoped profile values **and their profile_version together**. Render that version in each text/contact/photo form as `expected_profile_version`; absence of a profile is explicit version 0. Parse the HTML token as canonical ASCII decimal `0` or `[1-9][0-9]{0,9}`, bounded to 2,147,483,647, not a coerced boolean/float/array. Never derive the expected value from a fresh POST-time load. A profile_id/version pair is an untrusted selector for comparison, not account authority; retain current session, CSRF, active-account, authorization-version and portfolio ownership checks.
2. In a transaction, save only the action's supplied, editable, validated fields. Use one atomic compare-and-swap: `UPDATE personal_info SET <patch>, profile_version = profile_version + 1 WHERE id = :scoped_id AND portfolio_id = :authorized_portfolio_id AND profile_version = :expected AND profile_version < 2147483647`. Derive the scope from the authorized context and revalidate authorization at the write boundary. One row updated means success, including a same-value accepted save; zero means conflict/not-found/denied after safe scoped classification, **never** the current helper's “row still exists, therefore success” fallback. Do not retry stale input with a newly loaded version. An exhausted counter fails closed, without wrapping.
3. For a version-0 form, serialize creation under the owning User/Portfolio lock and require that a profile is still absent; unique `portfolio_id` remains the final constraint. A concurrently created/completed row makes that form stale. New creation/completion initializes version 1; an existing row is never upserted from an old absence form. Keep a consistent User → Portfolio → profile lock order when these locks are needed.
4. Return a safe 409 for a stale authorized form; keep the user's submitted text/visibility choices and **original expected version**, show a field/form-level explanation, and offer explicit reload/review/reapply. Do not replace inputs with `$savedProfile`, redirect as saved, silently merge, or attach a fresh version to old inputs. Authentication failures use existing denial paths without exposing another account's data. EN: “This profile changed after you opened the form. Your entries are kept here; reload and review before applying them again.” AR: “تغيّر الملف بعد فتح النموذج. احتُفظ بما أدخلته هنا؛ أعد التحميل وراجعه قبل تطبيقه مجددًا.” No persistent browser storage/body logging. A selected upload may need explicit reselection; never promise to preserve a browser file selection after navigation.
