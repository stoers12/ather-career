## Characterized path and scoped change

The path characterization below records the 2026-10-05 implementation checkpoint; the completion note above identifies subsequent deployment and callback-recovery changes.

`owner_login.php` rate-limits the request, checks Auth0 discovery and redirects to Authorization Code Flow with a server-session state, nonce and PKCE S256 challenge. `owner_oidc_callback.php` consumes the one-time transaction, exchanges the code, verifies the signed ID token and its issuer, audience, nonce and time claims, then resolves an internal User. On success it rotates the PHP session identifier, stores only the internal User ID, authorization version and bounded timestamps, and redirects by the existing portfolio-ownership check. Owner routes recheck active User state, authorization version and portfolio ownership. Logout remains CSRF-protected POST, destroys the local session and redirects to Owner login. Denial destroys the session and returns a generic 403; bounded security reasons are logged without provider payloads. The pre-cutover characterization ran before the resolver edit.

The **old** `resolveAuth0InternalUser` selected `users` by `oidc_subject`, compared the configured issuer with the legacy issuer, and inserted a new active `users` row for an unknown subject. The **new** resolver requires the Migration 014 `user_identities` table and calls `findCompatibleIdentityUser` with the exact validated issuer and subject. The repository uses a parameterized binary pair lookup, checks the primary binding against both legacy columns, and returns only User ID, account state and authorization version. The configured issuer is the canonical HTTPS issuer from the existing OIDC configuration; the validated token issuer must match it byte for byte. Subject comparison remains byte exact and bounded to 255 bytes. No email or profile field participates in authentication.

An absent binding, unknown pair, wrong issuer or missing 014 table fails closed before session establishment. Malformed or oversized identity input and a nonprimary or legacy-conflicting binding fail closed. A repository consistency exception emits `oidc_identity_resolution` with the fixed reason `binding_conflict`; no issuer, subject, email, token, code or request body is logged. The callback retains its generic client error. A disabled User or invalid authorization version is denied under the existing active-User rule. No user, identity, portfolio or session is created for an unresolved identity. There is no registration, automatic linking, repair, merge or consolidation path.

The read-only repository retains its pre-014 fallback for separate compatibility consumers, but **the callback explicitly refuses that fallback**. The legacy `users.oidc_issuer` and `users.oidc_subject` columns remain for consistency checking and recovery; no migration or data rewrite occurs in Phase 2A. Existing state, nonce, PKCE, token validation, session, cookie, trusted-proxy, redirect, Owner authorization and public route code is unchanged.

## Recovery boundary and disabled capabilities

The original pre-rollout requirement was as follows and remains applicable to a separately authorized future callback change: before rollout, preserve the reviewed Git ref and a tested database/media recovery point, recheck five exact bindings and all ownership/protected hashes, and prove a quiesced rollout. A failed callback cutover requires traffic to remain quiesced while identity and data state are inspected. Do not blindly revert to the old callback: that code can create legacy-only Users without a 014 binding. A reviewed rollback or forward correction must preserve the 014 ledger and explicitly prevent new registrations. Database rollback, identity linking, tenant changes and callback deployment need separate owner approval. Auth0 Management API calls, new providers, account linking, registration and consolidation remain disabled in this local slice.
