## Bounded operation

`includes/auth0_registration.php` adds **`registerAuth0InternalUser(PDO, Auth0OidcConfiguration, Auth0ValidatedIdentity)`**. It accepts the existing representation of an already validated ID-token identity and returns only `user_id` and `authz_version`. It requires exception-mode PDO and refuses a caller-owned transaction before doing work. The configured issuer must satisfy the existing HTTPS root-issuer shape, be bounded to 2048 bytes, and agree byte-for-byte with the identity. Subjects are nonempty, at most 255 bytes, valid UTF-8, contain a non-whitespace character and no ASCII controls. Accepted issuer and subject strings are stored exactly: no trimming, case folding, Unicode normalization, prefix inference, or email matching.

A consistent active exact primary binding resolves to its original User and authorization version, even if the current email classification is false/unknown; it is a resolution, not new registration. Disabled, nonprimary, legacy-mismatched, or multiple-primary bindings fail closed. Migration 014's binding table is required. A genuinely new identity is accepted only when `auth0EmailVerifiedClassification(emailVerifiedClaim, hasNonemptyEmail)` is strictly true. The representation retains only the trusted nonempty-email classification, not the email address; no account search or link by email exists.

New User and primary binding INSERTs share one owned transaction. The existing `users.uq_users_oidc_subject` and binary `user_identities.uq_user_identities_pair` constraints are unchanged. A failed second INSERT rolls back the User. Only MySQL duplicate-key errors naming those identity constraints can enter race recovery; after rollback the exact committed binding is re-read and its compatibility, active status, authorization version, and sole-primary relationship are validated. Legacy-only collisions and same-subject/different-issuer collisions are denied without repair or reassignment. Unrelated SQL failures propagate; there is no generic retry or caller-work commit.

No production route includes or calls this operation. `resolveAuth0InternalUser()`, `owner_login.php`, `owner_oidc_callback.php`, the creation-readiness guard, signup disabling, sessions, and schemas are unchanged. Provider/connection metadata stays NULL, including for a Google-shaped subject. No User email, readiness store, Portfolio/profile, consent, draft, or publication is added. Active is the existing schema default for this strictly positive-only core; holding-state registration is outside this slice.
